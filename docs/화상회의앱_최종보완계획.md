# 설치형 소규모 화상회의 앱 최종 제작 계획

- 작성일: 2026-09-15
- 목표 플랫폼: Windows 11 x64 우선
- 최대 인원: 방장 포함 20명
- 핵심 운영 방식: 방장 PC가 회의 서버와 SFU 역할을 수행하는 서버리스 설치형 앱

---

## 1. 프로젝트 개요

### 1.1 목표

별도의 상시 운영 서버나 월 라이선스 비용 없이, 방장 포함 최대 20명이 음성·카메라·고화질 화면공유를 사용할 수 있는 설치형 화상회의 앱을 만든다.

### 1.2 핵심 가치

- 회의 내용과 미디어를 외부 서비스에 저장하지 않는다.
- 방장이 회의를 직접 열고 닫는다.
- 참가자는 초대코드 또는 초대 링크를 붙여넣어 접속한다.
- 문서·PPT·수업자료의 글자가 선명하게 보이는 화면공유를 최우선으로 한다.
- 별도의 회원가입이나 중앙 계정 시스템을 두지 않는다.

### 1.3 핵심 구조

- 방장 앱에서 mediasoup SFU와 시그널링 서버를 실행한다.
- 방장도 자신의 SFU에 접속하는 한 명의 참가자로 동작한다.
- 참가자는 방장 PC로 직접 연결한다.
- 공유기의 UPnP 포트 매핑이 성공하거나 수동 포트포워딩이 설정된 환경에서 외부 접속을 지원한다.
- STUN은 공인 주소와 네트워크 상태 확인에 사용하며, 닫힌 포트를 열거나 모든 NAT를 우회하는 수단으로 간주하지 않는다.

### 1.4 지원 조건

외부 회의를 열려면 방장 환경이 다음 조건을 충족해야 한다.

- 공인 IPv4를 사용하는 인터넷 회선
- UPnP 사용 가능 또는 수동 포트포워딩 가능
- Windows 방화벽에서 앱 및 지정 포트 허용
- 유선 연결 권장
- 안정적인 업로드 200Mbps 이상, 300Mbps 이상 권장
- 4코어 8스레드 이상 CPU, RAM 16GB 이상 권장

### 1.5 지원하지 않는 환경과 한계

- 통신사 CGNAT 환경에서는 별도 중계 서버 없이 외부 회의 개설이 어렵다.
- 회사·학교·공공기관 방화벽이 인바운드 연결을 차단하면 방장이 회의를 열 수 없을 수 있다.
- 카페 와이파이처럼 공유기 설정 권한이 없는 환경에서는 방장 기능을 보장하지 않는다.
- 방장 PC가 종료되거나 네트워크가 바뀌면 회의가 종료될 수 있다.
- 서버 비용 0원과 모든 네트워크에서의 접속 성공을 동시에 보장하지 않는다.
- MVP에서는 IPv4만 지원하고 IPv6 및 TURN 연동은 후속 버전으로 검토한다.

### 1.6 MVP 범위 밖 기능

- 회원가입 및 클라우드 계정
- 서버 녹화 및 클라우드 녹화
- 회의 예약과 이메일 초대
- 모바일 앱과 브라우저 참가
- 참가자를 이용한 P2P 릴레이 또는 참가자 TURN 기능
- 대규모 웨비나
- 모든 참가자 카메라의 동시 고화질 전송

## 2. 제품 운영 원칙

### 2.1 최대 인원 정의

- 최대 20명은 방장을 포함한 동시 접속자 수다.
- 20명 회의에서는 화면공유와 음성을 우선한다.
- 전체 참가자의 카메라를 동시에 고화질로 전송하지 않는다.
- 참가자 목록은 20명을 모두 표시하되 실제 영상 구독 수는 화면과 네트워크 상태에 따라 제한한다.

### 2.2 품질 우선순위

1. 음성이 끊기지 않을 것
2. 공유 문서의 글자를 읽을 수 있을 것
3. 발표자 영상이 자연스러울 것
4. 나머지 참가자 카메라 품질

### 2.3 기본 회의 모드

| 모드 | 기본 동작 | 권장 상황 |
|---|---|---|
| 발표 모드 | 화면공유 1개 크게 표시, 발표자 카메라 우선, 나머지는 저화질 타일 | 수업·회의·발표 |
| 대화 모드 | 최근 발언자 6명까지 영상 수신, 나머지는 프로필 표시 | 토론 |
| 전체 보기 | 최대 20명 타일 표시, 비활성 참가자는 정지화면 또는 초저화질 | 출석·인원 확인 |
| 저대역폭 모드 | 음성 우선, 화면공유 720p, 카메라 수신 최소화 | 불안정한 회선 |

## 3. 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 데스크톱 앱 | Electron + TypeScript | Windows 11 x64 우선 |
| UI | React + Tailwind CSS | 컴포넌트 구조와 상태 관리 명확화 |
| SFU | mediasoup | 방장 PC에서 Worker/Router 실행 |
| 클라이언트 미디어 | mediasoup-client + WebRTC API | Electron Renderer에서 실행 |
| 시그널링 | WebSocket Secure 또는 인증된 WebSocket | 메시지 스키마 검증 필수 |
| 외부 주소 확인 | STUN | 공인 주소 탐지용이며 포트 개방 수단이 아님 |
| 포트 매핑 | UPnP 우선, 수동 포트포워딩 안내 | 후속으로 NAT-PMP/PCP 검토 |
| 초대 데이터 | CBOR 또는 MessagePack + Base64URL | 버전 확장 가능한 포맷 |
| 로컬 설정 | electron-store 또는 검증된 JSON 저장 | 민감 토큰 영구 저장 금지 |
| 패키징 | electron-builder | 네이티브 실행 파일 unpack 처리 |
| 배포 | GitHub Releases | MVP는 수동 업데이트 우선 |
| 테스트 | Vitest/Jest + Playwright + 다중 PC 실험 | 네트워크 장애 테스트 별도 |

## 4. 시스템 구조

```text
[방장 앱]
 ├─ Electron Main
 │   ├─ mediasoup Worker / Router
 │   ├─ WebRtcServer: 미디어 UDP/TCP 수신
 │   ├─ WebSocket 시그널링 서버
 │   ├─ UPnP 포트 매핑 및 네트워크 진단
 │   ├─ 회의 인증·권한·참가자 상태 관리
 │   └─ 종료·오류·로그 관리
 │
 ├─ Preload
 │   └─ 검증된 최소 IPC API만 Renderer에 노출
 │
 └─ Renderer
     ├─ 방장 UI
     └─ 방장 본인의 mediasoup-client

[참가자 앱 × 최대 19]
 ├─ 초대코드 해석 및 방장 인증서 확인
 ├─ WebSocket 시그널링 연결
 ├─ mediasoup-client 미디어 송수신
 └─ 네트워크 상태에 따른 화질 자동 조정
```

### 4.1 포트 설계

MVP에서는 설정과 문제 해결을 단순화하기 위해 고정 포트를 기본값으로 사용한다.

| 용도 | 기본 포트 | 프로토콜 |
|---|---:|---|
| 시그널링 | 44330 | TCP |
| WebRTC 미디어 우선 | 44331 | UDP |
| UDP 차단 시 미디어 대체 | 44331 | TCP |

- mediasoup `WebRtcServer`를 사용해 여러 WebRTC Transport가 하나의 미디어 UDP/TCP 포트를 공유하게 한다.
- UPnP에서 TCP 44330, UDP 44331, TCP 44331을 각각 매핑한다.
- 포트 충돌 시 앱이 대체 포트를 선택하고 초대코드에 반영한다.
- Windows 방화벽 허용 상태와 실제 외부 도달 가능성을 회의 시작 전에 검사한다.

## 5. 초대코드 및 접속 인증

### 5.1 초대코드 구성

```text
[버전]
[주소 유형]
[공인 IPv4]
[시그널링 포트]
[미디어 포트]
[128비트 이상 회의 토큰]
[방장 인증서 공개키 지문]
[만료시간]
[체크섬]
```

- 데이터를 CBOR 또는 MessagePack으로 직렬화하고 Base64URL로 인코딩한다.
- 사람이 직접 타이핑하기보다 복사·붙여넣기를 기본 사용 방식으로 한다.
- `smallmeet://join/...` 형태의 커스텀 프로토콜 링크와 일반 초대코드를 함께 제공한다.
- QR 코드는 후속 편의 기능으로 추가할 수 있다.

### 5.2 인증 원칙

- 4바이트 비밀번호 해시는 사용하지 않는다.
- 회의 생성 시 암호학적으로 안전한 128비트 이상의 무작위 토큰을 만든다.
- 방장 측에는 토큰 원문 대신 검증용 해시를 보관한다.
- 참가자가 인증되면 해당 연결에만 유효한 단기 세션 권한을 발급한다.
- 연속 인증 실패, 메시지 폭주, 비정상 패킷에는 속도 제한을 적용한다.
- 초대코드는 회의 종료 또는 설정된 만료시간 도달 시 무효화한다.
- 방장은 입장을 잠그고 기존 초대코드를 즉시 폐기·재발급할 수 있다.
- 초대코드에 공인 IP가 포함된다는 점을 방장에게 명확하게 안내한다.

### 5.3 전송 보호

- WebRTC 미디어는 DTLS-SRTP를 사용한다.
- 시그널링은 가능한 경우 WSS를 사용한다.
- 설치 시 생성한 자체 서명 인증서를 사용할 경우 초대코드에 공개키 지문을 넣고 참가자 앱이 이를 고정 검증한다.
- 인증서 검증 실패 시 사용자가 임의로 무시하고 입장하지 못하게 한다.

## 6. 20명 기준 미디어 및 대역폭 설계

### 6.1 무제한 전송 시 예상치

방장 포함 20명, 원격 참가자 19명, 카메라 1Mbps, 화면공유 4Mbps를 가정하면 다음과 같다.

- 원격 카메라 19개를 다른 원격 참가자 18명에게 재전송: 약 342Mbps
- 방장 카메라를 참가자 19명에게 전송: 약 19Mbps
- 화면공유 1개를 참가자 19명에게 전송: 최대 약 76Mbps
- 오디오, 재전송, DTLS·RTP·TCP 오버헤드 추가
- 총 업로드가 약 450Mbps 이상까지 증가할 수 있음

따라서 20명 전원의 1Mbps 영상을 모든 사람에게 계속 전달하는 방식은 사용하지 않는다.

### 6.2 기본 품질 정책

| 항목 | 기본값 | 조정 범위 |
|---|---:|---:|
| 일반 카메라 | 360p, 250~400kbps | 180p~720p |
| 발표자 카메라 | 540p 또는 720p | 회선에 따라 자동 조절 |
| 동시 고품질 카메라 | 최대 1~2개 | 발표자·최근 발언자 우선 |
| 참가자별 동시 영상 구독 | 최대 6개 | 화면 크기와 회선에 따라 축소 |
| 비표시 영상 | 소비 일시 중지 | 오디오와 상태만 유지 |
| 화면공유 문서 모드 | 1080p, 5~15fps, 3~6Mbps | 글자 선명도 우선 |
| 화면공유 동영상 모드 | 720p/1080p, 30fps, 4~8Mbps | 시스템 오디오 선택 가능 |
| 오디오 | Opus mono | 네트워크 상태에 따라 조절 |

### 6.3 코덱 전략

1. VP9 SVC를 우선 검토한다.
2. VP8 simulcast를 기본 대체 경로로 둔다.
3. H.264를 호환성 대체 코덱으로 시험한다.
4. Router codec 설정, 클라이언트 RTP capability, 실제 Electron Chromium 지원을 함께 검증한다.
5. `setCodecPreferences()` 호출 여부만으로 지원 성공을 판단하지 않는다.

### 6.4 적응형 전송 정책

- 패킷 손실과 RTT가 증가하면 비활성 카메라 구독부터 줄인다.
- 화면공유 중에는 참가자 카메라 비트레이트를 자동으로 낮춘다.
- 작은 타일은 simulcast/SVC의 낮은 계층을 선택한다.
- 창 밖으로 스크롤된 영상은 소비를 일시 중지한다.
- 네트워크가 불안정할 때 영상보다 음성을 우선 보존한다.
- 방장 업로드 여유가 부족하면 최대 참가자 수 또는 화면공유 화질을 자동 제한한다.

### 6.5 방장 회선 권장 기준

| 회의 형태 | 안정적 업로드 권장치 |
|---|---:|
| 10명 이하, 화면공유 중심 | 100Mbps 이상 |
| 20명, 발표 모드 | 200Mbps 이상 |
| 20명, 다수 카메라 활성 | 300Mbps 이상 |

표시된 회선 상품 속도가 아니라 앱에서 측정한 실제 업로드 품질과 패킷 손실을 기준으로 판단한다.

## 7. 주요 기능

### 7.1 필수 기능

- 방 생성·종료
- 초대코드·초대 링크 생성과 재발급
- 참가자 최대 20명 제한
- 카메라·마이크 장치 선택 및 켜기/끄기
- 문서형·영상형 화면공유
- 화면공유 시스템 오디오 선택
- 발표 모드·대화 모드·전체 보기
- 참가자 목록 및 최근 발언자 표시
- 방장 강퇴·전체 음소거·입장 잠금
- 텍스트 채팅
- 네트워크 품질 표시
- 연결 전 네트워크 진단
- 자동 재연결
- 방장 PC 잠자기 방지

### 7.2 네트워크 진단 화면

회의 생성 전에 다음을 순서대로 확인한다.

1. 로컬 IP와 공유기 탐지
2. 공인 IPv4 확인
3. CGNAT 의심 여부 확인
4. UPnP 지원 여부 확인
5. 시그널링 TCP와 미디어 UDP/TCP 포트 매핑
6. Windows 방화벽 상태 안내
7. 외부 도달 가능성 검사
8. 실제 업로드 속도·RTT·패킷 손실 검사
9. 예상 지원 인원과 권장 화질 표시

결과 예시:

- 초록: 외부 회의 가능, 20명 발표 모드 권장
- 노랑: 외부 회의 가능, 최대 10명 또는 저대역폭 모드 권장
- 빨강: 포트 접근 불가, 수동 포트포워딩 필요
- 회색: CGNAT 또는 관리형 네트워크로 외부 방 개설 미지원

### 7.3 오류 및 재연결

- WebSocket 연결이 끊기면 지수 백오프로 재연결한다.
- 재접속 참가자의 자리를 일정 시간 유지한다.
- ICE·DTLS 실패 시 해당 Transport를 폐기하고 재생성한다.
- 네트워크 인터페이스 변경을 감지해 연결 상태를 다시 검사한다.
- 카메라·마이크가 분리되면 대체 장치를 선택하도록 안내한다.
- mediasoup Worker 종료를 감지하고 안전하게 회의를 종료하거나 Worker를 재기동한다.
- 참가자 하나의 오류가 전체 회의를 종료시키지 않도록 격리한다.
- 방장 공인 IP가 바뀌면 기존 참가자에게 자동으로 새 주소를 전달할 수 없음을 알리고 회의를 재생성한다.
- 정상 종료 시 UPnP 포트 매핑을 제거하며, 비정상 종료 후 남은 매핑은 다음 실행 시 정리한다.

## 8. Electron 보안 원칙

- `nodeIntegration: false`
- `contextIsolation: true`
- Renderer sandbox 활성화
- Preload에서 허용된 최소 기능만 노출
- 모든 IPC 입력을 스키마로 검증
- 강한 Content Security Policy 적용
- 외부 웹 콘텐츠와 임의 URL 로딩 금지
- 새 창과 외부 링크 열기 정책 제한
- WebSocket 메시지 종류·크기·빈도 제한
- 채팅 길이 및 전송 빈도 제한
- 참가자 수를 UI가 아닌 서버에서 강제
- 파일 시스템과 셸 실행 기능을 Renderer에 노출하지 않음
- 로그에 회의 토큰, 공인 IP 전체, 채팅 내용, 미디어 내용을 남기지 않음
- Electron·Chromium·mediasoup 보안 업데이트 정책 수립

## 9. 개인정보 및 데이터 처리

- 영상·음성은 회의 중 실시간 중계만 하며 기본적으로 저장하지 않는다.
- 채팅은 방장 메모리에만 유지하고 회의 종료 시 삭제한다.
- 회의 참가자 이름과 장치 설정은 필요 최소 범위만 로컬 저장한다.
- 충돌 로그는 사용자 동의 후 내보낼 수 있게 하며 민감정보를 제거한다.
- 녹화 기능을 후속 추가할 경우 모든 참가자에게 명확한 녹화 표시와 동의 절차를 제공한다.
- 앱 첫 실행 시 처리 정보, 외부 IP 노출, 방장 책임과 네트워크 한계를 안내한다.

## 15. 최종 제품 정의

이 앱의 1차 버전은 다음과 같이 정의한다.

> 공인 IPv4와 포트 개방이 가능한 유선 가정망에서 방장 PC를 SFU로 사용하여, 방장 포함 최대 20명이 음성 대화와 문서 중심 고화질 화면공유를 할 수 있는 Windows 설치형 화상회의 앱이다. 20명 회의에서는 음성과 화면공유를 우선하고, 카메라 영상은 발표자·최근 발언자·화면에 보이는 참가자 중심으로 선택 전송한다.

이 정의를 벗어나는 “어떤 네트워크에서나 접속”, “모든 카메라 동시 고화질”, “방장 장애 후 회의 유지”는 별도의 서버 또는 중계 인프라가 필요한 후속 목표로 구분한다.
